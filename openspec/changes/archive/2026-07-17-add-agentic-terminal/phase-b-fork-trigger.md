# Phase B deterministic `question.asked` trigger

## Chosen path

Use mitigation ladder rung 1: run a deterministic local OpenAI-compatible test model alongside the real `opencode serve` process, configure the Phase B scratch project to use that model, and have the model emit a real `question` tool call.

The Phase B fixture will:

1. Start a local deterministic model endpoint using the existing `TestLLMServer` behavior from `packages/opencode/test/lib/llm-server.ts`, or a fixture-local extraction of that same helper if package boundaries prevent direct reuse.
2. Write the scratch project's `opencode.json` with `testProviderConfig(modelUrl)` from `packages/opencode/test/lib/test-provider.ts` and start the real OpenCode backend with an explicit port.
3. Create a real session through `POST /session?directory=<scratch>` and send a real prompt using the `test/test-model` provider.
4. Queue a deterministic model response that calls the built-in `question` tool with exactly one question, `multiple:false` (or omitted), and two options. Queue a normal completion after the tool result so the real session can finish after the reply.
5. Observe the resulting `question.asked` through the app's existing real SSE stream and assert the fork banner renders.
6. Resolve the fork in the UI and assert the real `POST /question/{requestID}/reply` succeeds, the request disappears from `GET /question`, and the session continues.
7. For shape-gating coverage, repeat with a deterministic `question` tool call whose single question has `multiple:true`, and with a call containing multiple questions. Assert neither request becomes an Agentic Terminal fork; reject the pending requests through the real endpoint during cleanup.

The model response shape is already supported by `TestLLMServer.Reply.tool(name, input)`, and the test provider configuration explicitly enables tool calls. This avoids any dependence on a hosted model choosing whether to ask a question.

## Why this is honest

This exercises the production path end to end:

`real HTTP prompt -> real SessionPrompt/LLM tool dispatch -> built-in QuestionTool -> Question.Service.ask -> EventV2Bridge -> real backend SSE -> app stream wrapper -> live adapter -> fork UI -> real question.reply HTTP handler -> pending Deferred resolution`

The question request is created by `Question.Service.ask`, assigned a real `que_*` identifier, stored in the real pending-question map, and published as the real schema event. The UI reply reaches the production handler and resolves the same pending request.

The deterministic model endpoint is a controlled external model dependency, not a mock of app-to-server traffic. There is no `page.route`, MSW, `installSseTransport`, fabricated browser event, direct store mutation, or alternate SSE connection. The app still communicates only with the real `opencode serve` process, satisfying D6 and the Phase B no-mock criterion.

## Evidence supporting the choice

- `packages/schema/src/v1/question.ts` defines `question.asked` directly from `Question.Request`: an ID, session ID, and an array of question records. The conforming fork shape can therefore be generated by a normal built-in question tool call.
- `packages/opencode/src/question/index.ts` shows that `Question.Service.ask` creates the ID, inserts the pending request, publishes `Event.Asked`, and waits on a Deferred until reply or reject.
- `packages/opencode/src/tool/question.ts` is the production entry point from a model tool call to `Question.Service.ask`.
- `packages/opencode/src/server/routes/instance/httpapi/groups/question.ts` and `handlers/question.ts` expose only list, reply, and reject. There is intentionally no public “ask” route, so an HTTP-only test cannot honestly manufacture a pending question.
- `packages/opencode/test/lib/llm-server.ts` already provides deterministic streamed tool calls with `Reply.tool(name, input)` and a real local HTTP endpoint.
- `packages/opencode/test/lib/test-provider.ts` already configures an OpenAI-compatible provider with tool calls enabled against that endpoint.
- Plugin hooks cannot create this event honestly. The public plugin input has an SDK client, but the client has no question-ask endpoint; the `event` hook is observational, and the before/after tool hooks cannot access `Question.Service`.

## Options assessed

### Hosted model prompted to ask a question

Rejected. It uses the production path but is not deterministic: the model may answer directly, change tool arguments, or choose a nonconforming shape. It also adds credential, latency, and provider-availability dependencies to the gate.

### Plugin hook that publishes or asks a question

Rejected. The plugin API exposes event observation and tool/chat transforms, not `Question.Service.ask`. Adding an ask API or importing server internals into a plugin would change server/plugin contracts, exceed this change's scope, and create a test-only production surface.

### Direct in-process `Question.Service.ask`

Useful for server unit tests, as demonstrated by `packages/opencode/test/question/question.test.ts`, but rejected for the Phase B Playwright flow. A separately started real server owns a different service instance, so direct test-process access would not create a pending request in the server the browser uses.

### Hand-inject `question.asked` into the app's real store entry path

Not chosen because rung 1 is available. Injection could test adapter rendering but would not create a real pending backend request, so the reply endpoint would have nothing to resolve unless paired with a separate server-side mechanism.

### Retain Phase A fork certification plus live reply smoke

Not chosen because rung 1 covers the complete path deterministically. This fallback remains appropriate only if the deterministic local model endpoint becomes technically unavailable in the Phase B runtime.

## Phase B implementation constraints

- Keep the deterministic model server in the Playwright fixture process; do not ship it in app or server production code.
- Bind both model and OpenCode servers to explicit loopback ports and wait on readiness without arbitrary sleeps.
- Use a unique scratch directory and session per test; delete the session and reject any pending question during cleanup.
- Configure one Playwright worker for fixed-port runs, or allocate per-worker ports.
- Audit the Phase B specs for `page.route`, MSW, `installSseTransport`, and direct event/store injection; all must be absent.
- Capture the browser trace plus the real server access log showing the prompt, question list/reply, and session cleanup calls.
